# CampusQuest — What We Built

**Databricks Campus Hackathon · BMSCE · Track A: Real-World Campus Problem Solver**

## The problem

Every student is told to "build projects" and "learn in-demand skills." Nobody
tells them **which** skills, or on what evidence. Advice on campus is
anecdotal — a senior's opinion, a LinkedIn post, a coaching centre's syllabus.

CampusQuest answers the question from placement history instead of opinion, and
shows its working every time.

## Architecture: two planes, on purpose

**Databricks (analytical plane)** — the campus dataset and Genie. Historical
postings, what each required, placements, opportunities, faculty research.
Every number the product displays is produced here by SQL.

**Supabase (operational plane)** — identity and live state. Google sign-in,
profiles, XP, quests, chat, connections, under row-level security, with
Realtime for messaging.

We deliberately did not put everything in one place. Delta is columnar
analytics storage: we measured single-row writes at ~1.6s versus ~0.5s on
Postgres, which would make chat unusable. Databricks also has no end-user
authentication and no per-app-user row security. Each store does what it is
good at.

**The rule we hold to:** XP, levels, alignment and skill frequencies come from
SQL. Genie writes prose. If a number appears on screen, a query produced it.

## The data foundation

We built the data before the product. **15 tables, 3,497 rows**, generated by a
deterministic script (seed 31) so every figure is reproducible.

| Cluster | Tables |
| --- | --- |
| Student graph | students, student_skills, skills |
| Placement history | companies, job_roles, job_requirements, placement_history |
| Opportunities | opportunities, opportunity_skills, learning_resources |
| Research | professors, professor_research, research_projects, publications, research_area_skills |

`skills` is the join hub — student skills, job requirements and opportunity
requirements all reference the same ids, which is what lets one query travel
from "what this student knows" to "what roles wanted" to "which workshop closes
the gap."

Requirements are sampled from **per-role-family probability profiles**, not
assigned uniformly. Uniform assignment makes every aggregate converge on the
same percentage, so no gap is more urgent than another and every query returns
a flat answer. Profiles produce real clustering and a realistic near-miss
population — 182 of 221 students sit in the band where a small number of skills
would change their outcome.

**What running the data changed.** Our first dataset had DSA appearing in 100%
of backend roles. Real hiring data is never unanimous, and a column of round
numbers correctly reads as fabricated. The cause was a fallback that injected
the same head skills whenever sampling came up short. Removing it produced the
distribution we ship:

| Skill | Roles requiring | Share |
| --- | --- | --- |
| Data Structures & Algorithms | 37 | 84% |
| SQL | 30 | 68% |
| Java | 27 | 61% |
| System Design | 25 | 57% |
| Python | 25 | 57% |
| Git | 24 | 55% |

(Backend Engineer + Software Engineer, 44 historical roles.)

## Features

**1. Placement Time Machine.** What companies actually asked for, by role family
and year. Overall alignment, the roles behind the number, and the skills the
student is missing with frequency and impact for each.

**2. Career What-If.** Add a skill and watch alignment move. A profile aligns
with a role when it holds at least 50% of that role's requirement weight, where
a core skill counts double a preferred one.

The weighting is not a detail. Postings distinguish between what a team
considers essential and what it treats as a bonus, and a model that ignores
that distinction produces a number that looks precise and moves for the wrong
reasons. We arrived at this rule by testing candidate rules against the data
and keeping the one whose answers held up — the earlier version was internally
consistent and told students almost nothing useful.

The result is honest in both directions: closing a widely-required skill moves
alignment sharply, while a nice-to-have moves it a little without pretending to
unlock roles it does not.

**3. Opportunity Radar.** 80 internships, hackathons, workshops and
competitions, ranked by the historical weight of the gaps each closes — not
keyword overlap. Filters by type, difficulty and deadline. Saves persist.

**4. Research Matchmaker.** Traverses interest → research area → professor →
open project → publications. A project only ever appears under an area its
professor genuinely publishes in, so the recommendation carries its evidence.

**5. People & Guilds.** Matches on complementary skills, not identical ones —
two people who both know PyTorch make a worse team than one who knows PyTorch
and one who knows embedded systems. Connection requests and real-time chat, all
RLS-scoped.

**6. Quest & progression system.** Skill gaps become quests. The biggest gap
determines the recommended quest — a Docker gap yields the Docker quest, a NumPy
gap yields the gradient-descent quest. Completing one awards XP through an
atomic SQL function, levels up, earns badges, and re-measures alignment against
the warehouse rather than projecting it. Each gap carries a concrete next step
from the learning-resources catalogue: provider, hours, free or paid.

**7. Genie on every screen.** Not a sidebar on one page. Available from anywhere
behind the app shell, with suggested questions scoped to the current screen,
multi-turn follow-up, and the generated SQL one click away.

## How Genie is used

- 16 Unity Catalog tables and views attached, with column comments written for
  Genie rather than for humans — it reads them to decide what to join.
- Instructions that fix the alignment rule, forbid claiming hiring probability,
  and forbid surfacing individual students.
- 7 example question-to-SQL pairs covering the four product questions.
- Streaming: status, then generated SQL, then the result table, then the prose.
  SQL and table arrive around ten seconds before the written answer, so the user
  sees evidence while the sentence is still being composed.
- Answer caching keyed per student: a repeated question returns in under a
  second with the same real answer and the same real SQL.

## How we know the answers are right

Genie is not trusted, it is checked. A verification script asks a catalogue of
28 questions and for each one:

1. Re-executes Genie's own generated SQL and compares the result with the table
   it displayed. If those disagree, the answer did not come from that query.
2. Runs an independent query we wrote, for questions with a deterministic
   answer, and compares.

Last full run: 28 asked, 25 verified.

A third check is arithmetic. We know the totals — 205 historical roles, 22 per
family, 221 students, 80 opportunities. Any answer citing a role count above 205
is aggregating the wrong way, and that single check has caught real bugs.

## What we deliberately do not claim

The data is synthetic and we say so. It models a plausible engineering campus;
it is not BMSCE's.

We report alignment with historical role profiles, never a probability of being
hired. "Your profile matches 20 of 22 historical ML Engineer roles" is supported
by this data. "Docker gives you a 93% chance of an offer" is not, and we do not
say it.

The schema is shaped so an institution could substitute its own placement
records without changing the application or the Genie configuration. That is the
path from hackathon demo to something a placement cell could actually run.
